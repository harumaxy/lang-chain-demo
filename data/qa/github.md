# GitHub リポジトリ管理

## Q: 新しいリポジトリを作成する際の命名規則を教えてください。

Example株式会社のGitHubリポジトリ名は以下の命名規則に従ってください。形式：`{サービス種別}-{機能・役割名}` （すべて小文字、単語区切りはハイフン）。例：`api-user-service`、`web-admin-portal`、`infra-kubernetes-configs`、`lib-shared-utils`。サービス種別の一覧：`api`（バックエンドAPI）、`web`（フロントエンド）、`mobile`（モバイルアプリ）、`infra`（インフラ設定）、`lib`（共有ライブラリ）、`tool`（社内ツール）、`docs`（ドキュメント）。リポジトリ作成後は必ずREADMEとLICENSEファイルを追加してください。リポジトリの新規作成はエンジニアリングマネージャー以上の権限が必要です。

---

## Q: ブランチの命名規則はありますか？

ExampleではGit Flowに準じたブランチ命名規則を採用しています。`main`：本番リリースブランチ（直接pushは禁止）。`develop`：開発統合ブランチ。`feature/{issue番号}-{機能の概要}`：新機能開発（例：`feature/123-add-oauth-login`）。`fix/{issue番号}-{バグの概要}`：バグ修正（例：`fix/456-fix-payment-timeout`）。`hotfix/{バージョン}-{概要}`：本番緊急修正（例：`hotfix/v2.1.1-fix-critical-xss`）。`release/{バージョン}`：リリース準備（例：`release/v2.2.0`）。ブランチ名には日本語を使用しないでください。

## Q: プルリクエストを作成する際のルールを教えてください。

PRを作成する際は以下のルールに従ってください。1. PRのタイトルは変更内容を端的に表す英語または日本語で記載（例：「Add JWT authentication for API endpoints」）。2. PRテンプレート（`.github/pull_request_template.md`）に沿って説明を記載してください。3. レビュアーを最低1名以上アサインしてください（チームリードまたはドメイン知識のある社員）。4. セルフレビューを行い、不要なコメントや`console.log`が残っていないか確認してください。5. CIがすべてパスしていることを確認してからレビューをリクエストしてください。WIPのPRはタイトルに「[WIP]」を付けてDraft PRとして作成してください。

## Q: CIチェックにはどのような項目がありますか？

Exampleの主要リポジトリではGitHub Actionsで以下のCIチェックが実施されます：1. **Lint**：ESLint / RuboCop / golangci-lint（言語別）によるコードスタイルチェック。2. **Type Check**：TypeScriptの型チェック（`tsc --noEmit`）。3. **Unit Test**：各リポジトリのテストスイート実行。カバレッジが70%未満の場合は警告が表示されます。4. **Security Scan**：Snykによる依存ライブラリの脆弱性スキャン。5. **Build Check**：本番用ビルドが正常に完了するかの確認。CIが失敗した状態でのマージはリポジトリの設定で禁止されています。CIの設定変更はインフラチームに依頼してください。

## Q: 誤って機密情報（APIキーなど）をコミットしてしまった場合はどうすればよいですか？

機密情報の誤コミットは重大なセキュリティインシデントです。発覚次第、以下の手順を直ちに実施してください。1. 該当のAPIキー・シークレットを即座に無効化・ローテーションする（サービスのダッシュボードで実施）。2. #security-alertチャンネルにてセキュリティチームに報告する。3. `git filter-repo`または`BFG Repo Cleaner`を使用してコミット履歴からシークレットを削除する（詳細はセキュリティチームが支援）。4. リポジトリをforce pushして履歴を書き換える（セキュリティチームのレビューが必要）。5. インシデントレポートを作成する。たとえプライベートリポジトリでも、コミット後は即座に対処が必要です。

## Q: リポジトリのアーカイブや削除はどうすればよいですか？

使用しなくなったリポジトリの処理については以下の通りです。**アーカイブ**：読み取り専用にしてリポジトリを保存する場合は、エンジニアリングマネージャーに依頼してください。アーカイブ前にREADMEに「このリポジトリはアーカイブされています。後継プロジェクトは〇〇を参照してください」と追記することを推奨します。**削除**：リポジトリの完全削除はCTO承認が必要です。削除前に全データのバックアップが必須です。本番環境に影響するリポジトリの削除は原則として行いません。削除申請は情報システム部の申請フォームから行ってください。

## Q: コードレビューのガイドラインはありますか？

Exampleのコードレビューガイドラインは以下を参考にしてください。レビュアーは24時間以内（営業日）に初回レビューを行うことを目標にします。レビューコメントは建設的かつ具体的に記載してください。「なぜ変更が必要か」を説明するコメントを心がけてください。必須修正のコメントには`[MUST]`、提案・議論には`[SUGGESTION]`、感謝・称賛には`[LGTM]`プレフィックスをつけると明確です。レビューで意見が食い違った場合はSlackで直接議論し、解決策をPRコメントに記録してください。Approveは最低1名（200行以上の変更は2名）のレビュアーが必要です。
